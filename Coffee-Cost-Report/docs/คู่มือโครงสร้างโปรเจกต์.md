# คู่มือโครงสร้างโปรเจกต์ — Coffee-Cost-Report

ระบบรายงานต้นทุนการผลิต / Loss / Yield เมล็ดกาแฟ สำหรับแผนก **บัญชีต้นทุนสินค้า**
ใช้แทน (หรือครอบ) กระบวนการทำ Pivot Table ใน Excel ด้วยมือ

> เอกสารนี้เน้นอธิบาย **โครงสร้างโค้ดและการไหลของข้อมูล** เป็นภาษาไทย
> สำหรับที่มา สูตรคำนวณละเอียดรายชีต และประวัติการแก้ไขรายวัน ให้อ่านคู่กับ:
> - [`../CLAUDE.md`](../CLAUDE.md) — สถานะปัจจุบันของโปรเจกต์แบบละเอียด
> - [`../README.md`](../README.md) — ที่มาและ scope
> - [`source-analysis.md`](source-analysis.md) — วิเคราะห์ไฟล์อ้างอิงทีละชีต ทีละสูตร **(ต้องอ่านก่อนแก้ logic การคำนวณ)**
> - [`roasting-dashboard-analysis.md`](roasting-dashboard-analysis.md) — ที่มาของแท็บ Dashboard สรุป
> - [`../daily-reports/`](../daily-reports/) — log การทำงานรายวัน (อ่านไฟล์ล่าสุดก่อนเริ่มงานทุกครั้ง)

## 1. ภาพรวมระบบ

| หัวข้อ | รายละเอียด |
|---|---|
| ประเภท | เว็บแอปรายงาน (อ่านอย่างเดียว) + ปุ่ม Export เป็น Excel |
| ผู้ใช้ | แผนกบัญชีต้นทุนสินค้า |
| แหล่งข้อมูล | ไฟล์ SAP **MB51** export (ปัจจุบัน) → ต่อฐานข้อมูล DBA โดยตรง (Phase 2) |
| เนื้อหารายงาน | แยกตาม 4 order-type/ขั้นตอนการผลิต: **301 / 302 / 303 / 305** + แท็บ **Dashboard สรุป** |
| การ Deploy | ยังเป็น local dev เท่านั้น (`npm run dev`) — ยังไม่มี auth / hosting |

### 4 ขั้นตอนการผลิต (Stage)

| Prefix | ชื่อ | คำนวณอะไร |
|---|---|---|
| **301** | Preclean (ทำความสะอาดสารกาแฟ) | ปันส่วนต้นทุนใหม่ตาม %STD, สัดส่วนเกรด, Settlement Rule |
| **302** | Roasting (คั่ว) | สัดส่วนผสม (blend mix) ของ input, สัดส่วนต่อ output, %Yield/%Loss — ได้จาก MB51 ล้วน ไม่ต้องกรอกมือ |
| **303** | Packaging (แพ็ค) | Yield/Loss แบบคิดจากน้ำหนัก (ต้องรู้กรัม/ถุงของ FG) |
| **305** | Repacking (แบ่งบรรจุใหม่ แบรนด์ CPR/รีเทล) | โครงสร้างเหมือน 303 แต่ input เป็นถุงด้วย → ต้องรู้กรัม/ถุงทั้งฝั่ง input และ output |

> **สำคัญ:** แต่ละ stage สูตรไม่เหมือนกัน ไม่ใช่ template เดียวใช้ซ้ำ 4 รอบ —
> จึงมีไฟล์ `pivot*.ts` และ `Stage*Table.tsx` แยกกันคนละไฟล์

## 3. การรันโปรเจกต์

```bash
npm install
npm run dev      # เปิด http://localhost:3000
```

คำสั่งอื่น:

```bash
npm run build    # build production
npm run start    # รัน production build
npm run lint     # eslint
```

การใช้งานหน้าจอ:

1. ระบบอ่านไฟล์ MB51 ล่าสุดจาก `data/latest-upload.json` อัตโนมัติ (ฟอร์มอัปโหลดในหน้าจอถูก comment ไว้ชั่วคราว — ดูหัวข้อ 6)
2. เลือกช่วงเดือนด้วย **Month Range Filter** (มุมขวาบน)
3. สลับแท็บ **Dashboard Summary / 301 / 302 / 303 / 305**
4. กรอก master data ที่แก้ได้ inline (%STD, กรัม/หน่วย)
5. กดปุ่ม **Export** เพื่อดาวน์โหลดรายงานของ stage นั้นเป็น Excel

## 5. การไหลของข้อมูล (Data Flow)

```
ไฟล์ MB51 (.xlsx)
   │  POST /api/upload
   ▼
lib/parse.ts  ──►  RawMovementRow[]        (material, order, quantity, amount,
   │                                        postingDate, sLoc, mvt, batch)
   │  saveLatestUpload()
   ▼
data/latest-upload.json
   │
   │  ── app/page.tsx (server) เรียก loadLatestUpload() + loadStdMaster() + loadUnitWeightMaster()
   ▼
<ReportView>  (client)  ── state: activeStage, monthFrom/monthTo, stdMaster, unitWeightMaster
   │
   ├─ filteredRows = กรอง rows ตามช่วงเดือน (lib/dates.ts)
   │
   ├─ useMemo เรียกสูตรตามแท็บที่เปิด:
   │     301 → computeOrderReport(filteredRows, stdMaster)        → <Stage301Table>
   │     302 → computeOrder302Report(filteredRows)                → <Stage302Table>
   │     303 → computeOrder303Report(filteredRows, unitWeight)    → <Stage303Table>
   │     305 → computeOrder305Report(filteredRows, unitWeight)    → <Stage305Table>
   │     301 (การ์ดบน) → computeMonthly301Summary(...)            → <Monthly301SummaryView>
   │     Settlement Rule → computeSettlementRuleReport(rows ทั้งหมด, stdMaster) → <SettlementRuleModal>
   │     Dashboard → <DashboardOverview> เรียก computeSummaryDashboard() ภายใน
   │
   ├─ แก้ master data inline:
   │     กรอก %STD  → POST/DELETE /api/std        → setStdMasterEntry()  → std-master.json
   │     กรอกกรัม   → POST /api/unit-weight       → setUnitWeightMasterEntry() → unit-weight-master.json
   │     (อัปเดต state ทันที + ยิง API แบบ debounce แล้วคำนวณใหม่)
   │
   └─ ปุ่ม Export → GET /api/export?stage=&from=&to=  → lib/exportReport*.ts → ไฟล์ .xlsx
```

### จุดที่ต้องเข้าใจ

- **การคำนวณทั้งหมดเกิดฝั่ง client** ใน `useMemo` ของ `ReportView` — `page.tsx` แค่โหลด raw rows + master data มาให้ ทำให้กรอง master data แล้วเห็นผลทันทีโดยไม่ reload
- **`lib/store.ts` คือรอยต่อเดียว** ที่ Phase 2 จะเปลี่ยน — เขียน read path ใหม่ให้ map ชื่อคอลัมน์ของ DBA (`MB51_MATERIAL_CODE`, `MB51_ORDER`, ...) มาเป็น `RawMovementRow` โดย caller ทั้งหมดไม่ต้องแก้
- **Settlement Rule Report ใช้ rows ทั้งก้อน** (ไม่กรองเดือน) เพราะเป็น cross-tab รายปี — ต่างจากตาราง stage อื่นที่ใช้ `filteredRows`
- **แท็บ Dashboard จำแนกแถวคนละวิธี** กับแท็บ 301/302/303/305: ใช้ SLoc + movement type + material code ตามที่ชีต `เงื่อนไข` กำหนด (แม่นกว่าการเดาจากเครื่องหมาย +/- ของ quantity ซึ่งเคยเพี้ยน 10–34%)

## 6. Master Data ที่แก้ได้ (ไม่มีใน MB51)

| ข้อมูล | ไฟล์ | ใช้ที่ไหน | หมายเหตุ |
|---|---|---|---|
| **%STD** ต่อ material | `data/std-master.json` | สูตรปันต้นทุนใหม่ของ 301 | เก็บเป็น **ประวัติมีวันเริ่มผล** (`{from:"YYYY-MM", value}[]`) — เดือนเก่ายังใช้ค่าเดิม; ค่าเก่าที่เป็นตัวเลขเดี่ยวถูก migrate อัตโนมัติตอนอ่าน (sentinel `from="0000-01"`) |
| **กรัม/หน่วย** ต่อ material | `data/unit-weight-master.json` | แปลงจำนวนถุง → กก. สำหรับ Yield ของ 303/305 | ไฟล์ต้นฉบับ hardcode "500g" ในสูตร ซึ่งพังทันทีถ้าถุงขนาดอื่น |
| **FG code ที่ยืนยันน้ำหนักแล้ว** | `lib/fgUnitWeights.ts` (โค้ด ไม่ใช่ JSON) | Dashboard สรุป (ใช้ตัวนี้อย่างเดียว ไม่มี fallback) + 303/305 (ใช้ก่อน แล้วค่อย fallback ไป unit-weight-master) | 8 code: 500g เจ็ดตัว, 250g หนึ่งตัว, นอกนั้น `ELSE 0` ตามสูตรที่ผู้ใช้ยืนยัน |

> ฟอร์มอัปโหลดไฟล์และ header ในหน้าจอถูก **comment ไว้** ใน `ReportView.tsx` ระหว่างรอ Phase 2
> (`/api/upload` และ `lib/parse.ts` ยังทำงานได้ปกติ — เรียกผ่าน API ตรง ๆ ได้)

## 7. Phase 2 — ต่อฐานข้อมูล DBA โดยตรง (ตัดสินใจ 2026-09-01)

- เลิกอัปโหลดไฟล์ ต่อแอปเข้าฐานข้อมูล DBA ที่ RPA เติมข้อมูล MB51 (plant 0328) ให้ทุกวัน
- RPA เก็บย้อนหลัง ~6 เดือน; ผู้ใช้จะ backfill ข้อมูลเก่าลง DB เอง (เป้าหมายเก็บ 1 ปี) → แอปเป็น **ผู้อ่านอย่างเดียว** ไม่มีการสะสมประวัติในแอป
- งาน Dev หลัก: ชั้น DB access/secret, rewrite read path ใน [`lib/store.ts`](../lib/store.ts), ย้าย master data 2 ไฟล์ (%STD, กรัม/หน่วย) เข้าตาราง DB, scheduled read + cache, reconcile 1 เดือนที่ทับกับตัวเลขอ้างอิงที่ verify แล้ว, deploy ออกจาก local
- ประเมิน ~1.5–2 สัปดาห์ (1 dev) + เลือก hosting/datastore + DevOps provision
- ตัวอย่าง export จาก DBA: `../Reference-File/mb51_plant0328.csv`

รายละเอียดเต็ม + ข้อค้างคาที่ต้องเคลียร์กับ DBA อยู่ในหัวข้อ "Phase 2" ของ [`../CLAUDE.md`](../CLAUDE.md)
